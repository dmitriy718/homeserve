# Review pass 4 — production architecture and deployment

Date: 2026-08-11  
Depth: 8× baseline  
Perspective: production topology, observability, release identity, testability, boot behavior, host integration, and live/repository drift

## Scope and method

Extended all prior passes across the entire deployment lifecycle. Rendered the final Compose model, inspected capabilities of the pinned Prometheus/Grafana/Uptime/Speedtest images, built custom images, ran containerized regression tests, validated alert expressions with `promtool`, inspected the live host read-only for capacity/targets/restarts/drift, and reviewed systemd plus future GitHub runner activation.

Live evidence at review time: 12 Compose services running, 15/15 Prometheus targets up, zero container restarts/OOM kills, no failed systemd units, root storage at 8%, and approximately 9.8 GiB memory available.

## Findings and fixes

### P4-01 — Custom image release identities were stale

- Severity: medium
- Finding: materially changed gateway, embeddings, and NVIDIA exporter images still used `:1.0`, obscuring which behavior a container actually contained.
- Fix: bumped those images to `:1.1` and the gateway API version to `1.1.0`, making deployment and rollback inventories unambiguous.

### P4-02 — Custom services lacked regression tests and embeddings coupled import to model I/O

- Severity: high
- Finding: critical gateway authentication, secret isolation, atomic I/O, timeout cleanup, corrupt audit handling, embedding request limits, and GPU failure semantics were only manually exercised. The embeddings module also loaded its large model during import, coupling basic validation/tests to cache or network availability.
- Fix: added six gateway, five embeddings, and two NVIDIA exporter unit/regression tests inside their runtime images. Embedding model initialization moved to FastAPI lifespan startup, so request logic can be tested with a deterministic fake model while production still finishes loading before accepting traffic. Gateway/exporter tests run with their production user, read-only filesystem, dropped capabilities, and isolated network constraints. The validator runs tests when matching images are present and otherwise reports an explicit skip; the updater validates both before mutation and again after builds so newly created images must pass before startup.

### P4-03 — Three core web services lacked Docker health state

- Severity: medium
- Finding: Prometheus, Uptime Kuma, and Speedtest Tracker could be running but broken without Docker reflecting that state.
- Fix: added native readiness/HTTP health checks using tools verified in the exact pinned images. This brings them into unhealthy-container detection and Compose status.

### P4-04 — Grafana startup did not wait for Prometheus readiness

- Severity: medium
- Finding: Grafana depended only on Prometheus container creation, allowing avoidable datasource errors during startup.
- Fix: Prometheus now has a `promtool check ready` health check and Grafana waits for `service_healthy`.

### P4-05 — Backup freshness was invisible to metrics and dashboards

- Severity: high
- Finding: operators could inspect archives manually, but Prometheus could not detect a missed nightly backup and Grafana had no backup or alert summary.
- Fix: successful verified backups atomically publish a node-exporter textfile metric. Added stale-after-36-hours and missing-metric alerts, plus Grafana panels for backup age and total firing alerts.

### P4-06 — Boot reconciliation bypassed repository validation

- Severity: high
- Finding: the updater validated configuration, but systemd boot could start an invalid checked-out revision directly.
- Fix: `ai-node-stack.service` now runs strict repository validation before waiting for addresses or invoking Compose.

### P4-07 — Scheduled backup execution had no upper time bound

- Severity: medium
- Finding: a stalled archive or external target could leave the oneshot service active indefinitely.
- Fix: the backup unit now has a four-hour start timeout; the script's signal/exit cleanup unpauses services and removes incomplete artifacts when systemd terminates it.

### P4-08 — Future runner unit left avoidable host surfaces exposed

- Severity: medium
- Finding: the GitHub runner example had useful baseline controls but still exposed devices, kernel tunables/modules/logs, control groups, setuid creation, and personality changes.
- Fix: strengthened the example with `PrivateDevices`, kernel/control-group protections, `RestrictSUIDSGID`, `LockPersonality`, native syscall architecture enforcement, and `UMask=0027`.

### P4-09 — NVIDIA image builds could enter interactive package configuration

- Severity: medium
- Finding: the pinned CUDA base pulled `tzdata`; without a noninteractive install environment, unattended builds emitted a geographic prompt and depended on EOF fallback.
- Fix: the package installation step now explicitly uses `DEBIAN_FRONTEND=noninteractive`.

### P4-10 — Generated backup-health state polluted restore semantics

- Severity: low
- Finding: archiving the previous backup status/metric would make a restored server initially advertise stale archive paths and success timestamps.
- Fix: generated backup status and node-exporter textfile data are excluded from archives and regenerated only after a new verified backup.

### P4-11 — Validation omitted the optional development profile

- Severity: medium
- Finding: ordinary `docker compose config` excludes profile-gated services, so Playwright's seccomp, capability, network, and shared-memory configuration could regress without failing validation. JavaScript and its package metadata also lacked syntax/JSON checks.
- Fix: the validator now renders both default and `dev` profiles, parses the dashboard and both Playwright package files, and runs `node --check` when Node.js is available.

## Residual operational constraints (not code defects)

- Local backups remain on the same SSD until an external `BACKUP_DEST` is mounted.
- Prometheus alerts remain visible locally but do not send notifications because no Alertmanager receiver/contact destination was authorized.
- Agent shell execution intentionally retains outbound connectivity through its required AI/monitoring networks; authentication and container isolation remain the controlling boundary.
- This review changed the local codebase only. A separate reviewed deployment is required to alter the running server.
