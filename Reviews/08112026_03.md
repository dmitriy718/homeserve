# Review pass 3 — failure recovery and data integrity

Date: 2026-08-11  
Depth: 4× baseline  
Perspective: interruption, partial failure, rollback, concurrency, and durable state transitions

## Scope and method

Extended the earlier reviews across multi-step operations: archive creation through retention, image pull through health acceptance, boot reconciliation, process timeout behavior, file replacement, log rotation, and malformed persisted data. Examined what remains after signals, disk/write failures, unhealthy deployments, concurrent requests, and truncated records.

## Findings and fixes

### P3-01 — Backup archive/checksum publication was not transactional

- Severity: high
- Finding: the archive became final and the cleanup trap was removed before its checksum and status record were safely published. Interruptions could leave a final archive without a valid sidecar, or a partial checksum with a final name.
- Fix: archive, checksum, and status publication now share one cleanup transaction. Both payloads use partial names, checksum verification occurs before commit, and any pre-commit failure removes incomplete/final artifacts. The status record is also published atomically.

### P3-02 — Mutable gateway and ComfyUI data remained live during backup

- Severity: high
- Finding: the backup included gateway workspaces/audit data and ComfyUI inputs/outputs while those services could write them, producing internally inconsistent archives.
- Fix: `agent-gateway` and `comfyui` join the existing stateful-service pause set. The exit/signal trap always unpauses every successfully paused service.

### P3-03 — Failed updates had no automated image rollback

- Severity: high
- Finding: pulls/builds overwrite image tags, and a partially recreated or unhealthy stack required manual recovery even though old image IDs still existed.
- Fix: the updater snapshots every running service's image ID before mutation. Pull/build/config failures restore old tags; recreation or health failures restore tags, reconcile the previous stack, and run the full health gate again. Automatic rollback failure is reported explicitly.

### P3-04 — Every boot force-recreated all containers

- Severity: medium
- Finding: systemd used `--force-recreate`, turning every reboot into an avoidable full redeployment and increasing migration/startup failure exposure.
- Fix: boot now performs an idempotent `compose up -d --remove-orphans`; containers are recreated only when their effective configuration or image requires it.

### P3-05 — Timed-out shell descendants could survive

- Severity: high
- Finding: `subprocess.run(..., timeout=...)` terminates the immediate shell but may leave descendant processes running.
- Fix: each command starts in a new process session. Timeout sends SIGTERM to the full process group, waits five seconds, then sends SIGKILL if required and collects remaining output.

### P3-06 — Gateway file overwrites were not atomic

- Severity: medium
- Finding: direct writes could leave a truncated destination after interruption, and append operations could partially apply.
- Fix: writes and appends now build the complete bounded content in a same-directory temporary file, flush and `fsync` it, atomically replace the destination, and `fsync` the containing directory. Binary append attempts are rejected.

### P3-07 — Audit and HTTP resource handling was fragile

- Severity: medium
- Finding: concurrent audit writers could race rotation, one truncated JSONL line broke the audit endpoint, HTTP responses relied on garbage collection for closure, and hashing loaded the whole file into memory.
- Fix: rotation/appends use a process lock, malformed audit lines are skipped, HTTP/socket resources use context managers, and hashes stream in 1 MiB blocks.

## Verification

- Shell syntax and static analysis cover the transactional backup and rollback logic.
- Runtime timeout, atomic-write, audit-corruption, and rollback-structure tests are included in the cumulative pass-4 verification.

## Residual considerations

- A host power loss can still interrupt the underlying filesystem or Docker daemon; atomic rename/fsync and verified archives minimize but cannot eliminate hardware-level loss.
- External changes to `/srv/repos` are not governed by the Compose pause set. Coordinating external writers remains an operator responsibility during the short backup window.
